# 评测

一套商品内容治理系统，判一个商品该放行（PASS）、该下架（REJECT），还是拿不准交给人（HUMAN_REVIEW）。
系统里有确定性规则、一次模型调用、多步调查 Agent 三种做法。这份文档说明怎么评它们：每套方案能看到什么
信息、评测集怎么造、每个指标怎么算、最近一次结果是什么，以及这些数字能说明什么、不能说明什么。

结果那一节只保留最近一次运行，重跑就整节覆盖。其余部分写的是评测本身，不随代码改。

## 三个方案

三套方案看同一份商品事实，差别只在允许看到多少信息。这是可比性的前提：谁都不能看到别人看不到的材料。
共同输入就是商品本身：标题、描述、属性、类目、品牌、SKU、图片，以及机审已经产出的图片文字（OCR）。

**Rule：只用确定性规则。** 对这份事实跑黑名单品牌、违规关键词、类目规则、图片 Logo、OCR 关键词、
风险分阈值，命中黑名单品牌这类硬规则就直接判 REJECT。规则判 PASS 记 PASS，判 REJECT 记 REJECT，
判"复杂，需要进一步查"记 HUMAN_REVIEW —— 在没有 Agent 的世界里复杂案只能交给人。注意线上是"复杂案交给
Agent 终裁"，评测里是"复杂案交给人工"，两者不是一回事。

**一次模型调用（Single-call）：只让模型看一遍。** 把整份事实一次交给模型，模型直接回一个决策 JSON。
刻意不给商家历史、案例库、政策库 —— 那些是 Agent 靠工具查出来的，先塞给模型就是作弊。
模型自报的信心分低于**本方案自己的置信门槛**时转人工（默认 0.7，取值以代码为准），所以这一套也有 HUMAN_REVIEW。
它恒为"基础输入原样"一种形态，没有预塞政策或先例文本的变体。

**Agent：允许主动调查。** 按证据缺口动态调工具，查商家历史、相似案例、政策条款、图片相似度，
多步推理后再下结论，同样有转人工出口。终裁必须经事实证据与 Gate 校验，不采信模型自报的假设与置信度。

三套方案都输出 PASS / REJECT / HUMAN_REVIEW，都写进同一条记录、交给同一套指标计算，否则没法比。
记录里有决策、风险等级、风险类型、信心分、证据列表、引用的政策条款、实际调用的工具，以及成本
（模型调用次数、工具调用次数、token 数）。记录里还带一段调查轨迹供 Agent 专用指标取数：每次工具调用
前后的信心变化、是否带来新证据、是否让结论翻转。桩臂要求同一案重跑结果一致（基本可重复性，用于 CI 回归）；真实模型臂不做可重放要求。

## 评测集

### 怎么造

一条评测集案例包含唯一编号、场景标签、来源类型、程序化变异的溯源、是否难例及难例原因、商品事实快照，
以及期望答案。期望答案不只有 PASS/REJECT，还包括风险等级、风险类型、期望证据类型、Agent 应该调用哪些
工具、应该引用哪条政策 —— 这样评测才能区分"结论蒙对了但理由错了"。

四条来源：

1. **人工构造对抗样本**：核心是品牌模仿与规避，比如没有 Logo、没有品牌词，但外观高度相似，商家还有违规史。
2. **真实案例改写脱敏**：把历史上的人工裁决案件脱敏成评测条目，个人信息和商家联系方式不入库。
3. **程序化变异**：对模板做字段变异制造边界案，比如改相似度、改商家历史、制造 OCR 与描述冲突，
   用固定随机种子，产物可重复生成。
4. **人工标注**：每条都标期望决策、证据、政策、期望工具。做法上要求多人标注、冲突的案子改到一致；
   **当前数据集只有一名标注者，没有交叉校验**（见下面的已知局限）。

合成与变异由脚本生成，方便复现；真实脱敏改写入库，方便评审。数据集按版本存放、随代码一起入版本库，
配一个 manifest 记录分布统计、难例占比、生成方式以及标注一致性。

### 多少条、怎么分布

判定类真值只有 PASS 和 REJECT 两种，另有少量"本该转人工"的案。五类场景按下面比例分层抽样，
避免案型偏斜，每类允许 ±5 个百分点的偏差。正式集目标 300 条以上，每类真值都必须明确，
不为了凑比例塞数据。

| 场景标签 | 占比 | 说明 |
|---|---|---|
| `normal` 明确正常 | 20% | 规则与 Agent 都应 PASS |
| `violation` 明确违规 | 20% | 规则与 Agent 都应 REJECT |
| `boundary` 边界案件 | 30% | 规则拿不准、单个信号弱 |
| `multi-signal` 多信号组合 | 20% | 需要多源交叉验证 |
| `evasion` 对抗/规避 | 10% | 刻意规避审核，是难例的主体 |

### 什么算难例

满足任意一条就算难例，并在数据里标出来：① 规则判不了或容易判错；② 一次模型调用证据不足或不稳定，
要下结论必须用到输入里根本不存在的信息；③ Agent 多步调查能拿到额外证据，调工具能明显改变结论。
第 1、3 条在跑过分数后回填确认，第 2 条由标注者按证据缺口判断。难例占比目标 15% 以上
（`evasion` 那 10% 加上 `boundary` 里符合上面三条的）。

### 已知局限

- **只有一个标注者**。真值由生成器按与评测审查员同源的规则程序化标注，没有第二个人交叉校验，
  所以高分只说明"实现和标注规则一致"，不能外推成"调查能力强"。
- **没有内容重复的案**：去重保证不存在只差商品 ID、版本号、上架时间的重复行，但标题里的核心词
  仍然跨案复用，表观多样性有限。
- **期望工具为空 = 没标注**，不是"应该调用 0 个工具"，这类案不计入工具选择指标的分母。
- **真实模型只跑过单次**，没有重复采样，它只能证明真实链路跑得通，不代表模型水平。

## 指标怎么算

### 先分清两个世界

- **可重放世界（桩臂的确定性属性，不是全项目要求）**：模型用桩（固定脚本回答），工具读内存里的种子数据。
  同一案重跑结果一致，适合放进 CI 当回归。它衡量的是实现和规则是否自洽。种子是最小实现，不要求与真实库逐项等价。
- **真实世界**：模型是真模型，工具接真数据库和真检索。结果不确定，不做可重放要求。

两个世界的数字不能混着读，也不能拿一个去暗示另一个。工具也不同：评测世界用 5 个工具
（商品 / 图片分析 / 商家 / 案例检索 / 政策检索），生产工具集里还多一个 OCR 工具，评测集从不期望它。

评测输入的图片 url 是**中性资源 ID**，不含 clean / viol / bound / logo 这类路径语义 ——
真实模型会连 url 字面一起看到，语义化路径段等同于把真值类目直接告诉它。这条不变量由测试守住。

下面用到三个说法。**拿不准就交给人**（abstention）：系统不硬判，输出 HUMAN_REVIEW；这是克制不是错误，
也不能当普通第三分类混进准确率。**有明确对错的案**：
真值是 PASS 或 REJECT 的案，大多数指标的分母用它。

### 主指标表

| 指标 | 它回答什么问题 | 分母 | 数据从哪来 |
|---|---|---|---|
| Accuracy 准确率 | 判对了多少 | 有明确对错的案；**输出转人工也算错** | 预测决策 × 期望决策 |
| Precision 精确率 | 判 REJECT 的有多少是真违规（判错会误伤商家） | 所有被判 REJECT 的案 | 同上 |
| Recall 召回率 | 真违规的抓出来多少（漏放会损害平台） | 真值是 REJECT 的案 | 同上 |
| False Positive Rate 误杀率 | 正常商品被自动下架的比例 | 真值是 PASS 的案 | 同上 |
| False Negative Rate 漏放率 | 违规商品被自动放行的比例 | 真值是 REJECT 的案 | 同上 |
| human_review_rate 转人工率 / automation_coverage 自动化率 | 人工要接多少活、多少案是自动定的 | 全部案 | 预测决策 |
| abstention_rate 过度转人工率 | 本来能自动判却交了人 | 真值明确的案 | 预测决策 |
| abstention_recall 该转就转的召回 | 该交人的案交了人没有 | 真值是该转人工的案 | 预测决策 |
| wrong_auto_decision_rate 自动判错率 | 自动定下来的案里错的比例 | 所有自动定下来的案 | 预测决策 |

几条容易踩的坑：准确率的分母包含转人工的案，转人工按错算，这比"只算自动判决的案子"更严，
是为了逼着自动化率和误杀率一起看，否则"大量转人工"的方案会显得很准；误杀率、漏放率、精确率、
召回率的分母只含对应真值类，预测转人工不计入；转人工率和自动化率的分母是全部案（320），
跟准确率的 274 不是一回事。**自动化必须和安全一起读** —— 只有方案能把复杂案里的一部分安全地自动化
（自动化率上升，同时误杀率和漏放率不恶化）时，才谈得上是价值。

### Agent 专用指标

| 指标 | 它回答什么问题 | 分母 | 数据从哪来 |
|---|---|---|---|
| Tool Selection Accuracy 工具选择准确率 | 该调的工具调了没有 | 标注了期望工具的案 | 期望工具集合 × 实际调用集合 |
| redundant_tool_rate 多余调用率 | 调了多少没必要的工具 | 全部案 | 实际调用集合 |
| Evidence Type Coverage 证据类型覆盖 / REJECT 依据前置合格率 | 期望的证据类型拿到多少、判下架的是否都有可引用依据 | 期望证据类型数 / 预测 REJECT 的案 | 期望证据 × 实际证据、证据链 × 政策条款 |
| risk_type_coverage 风险类型命中率 / risk_level_agreement 风险等级一致率 | 风险类型和风险档位说对了多少 | 真值是 REJECT 的案 / 全部案 | 期望值 × 输出值 |
| evidence_gain_rate 有效取证率 / decision_changed_rate 结论翻转率 / Marginal Evidence Gain 边际证据增益 | 工具调用里多少带来新证据、多少改变结论、每次涨了多少信心 | 全部工具调用（增益只看有效调用） | 调查轨迹 |

取数规则：期望工具、期望证据、期望风险类型为空的案不进分母；证据覆盖只按能映射上的类型算，不硬猜；
结论对但推理错要靠抽样人工复核，自动化只能近似。**预算占用率不出数** —— 它不是"再补一个指标"的事：
记录里没有随案冻结的预算上限，硬算只能拿当前配置去套历史运行，那是**伪造观测**；真要做，先让预算快照
随案落库。

### 成本怎么记

每个方案报模型调用次数、工具调用次数、token 数的均值、P50、P95、最大值。桩模式里的 `tokens=0`
是真实值 —— 桩不烧 token（`usage.total_tokens` 恒为 0），不填估算值上去。延迟只有真实世界才有，
桩模式不出延迟数字（延迟是进程相关的墙钟量，不进可比较口径）。

### 阈值不随数据集调

外观相似度的分档、预算上限都是**工程初始值**，写在生产真正读它的那处常量里，
**没有在评测数据集上拟合过，也不会因为评测结果回改**；具体取值以代码为准。

评测侧曾经有过"扫一遍阈值看曲线"的工具，已经删掉，理由有两条：被扫的阈值只作用于**评测侧的审查员**，
跟生产实际读常量的位置不是同一处，把结论写回去等于把它用在没测过的层级上；而且评测数据在阈值附近
没有案子，曲线要么平要么接近平，对决策没有指导意义。

将来真要校准生产阈值，得先把可配置点下沉到生产读常量的位置，并把阈值附近的案子补齐 —— 那是另一次设计，
不是在评测里加回扫点。同理，评测不会为了"方便观察"放宽生产预算档位。

## 这些数字能说明什么、不能说明什么

- **可重放世界衡量的是实现自洽，不是模型能力**。它的高分里含"标注规则与审查规则同源"的成分，因为真值按
  同一套规则程序化标注，而且只有一个标注者，所以不能外推到线上成绩。
- **真实世界只代表那一次运行**：单次、单模型、非确定性，也没做提示词调优和重复采样；它不能当成
  模型固定水平，更不能拿去反推或对冲可重放世界的数字。
- **两个世界不能混读**：指标名相同，含义不同，引用任何一个都要说明它来自哪个世界。**`tokens=0` 是可重放
  世界的真实情况**，桩不烧 token，不填假值。
- **种子数据覆盖有限**：种子里没有的真实先例和完整规避史 Agent 查不到，多信号和对抗类案的证据充分度、
  边际证据增益会被低估，真实检索与数据库接入后要用真实世界复核。
- **生产侧的限制如实声明**：图片分析与 OCR 还是桩，装配时明确声明为"不可测"，免得把"测不出来"误判成
  "测过且没问题"；后果是生产入口对带图案件在拿到真实视觉数据源之前不会自动放行，这是已声明的缺口。
  单一商家的历史画像也不能单独作为自动下架依据，必须有本案商品的外观或文本信号佐证。
