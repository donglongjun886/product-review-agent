# 评测

一套商品内容治理系统，判一个商品该放行（PASS）、该下架（REJECT），还是拿不准交给人（HUMAN_REVIEW）。
正式评测只跑**真实数据 × 真实模型 × 固定 Eval World**：模型是真模型，工具接随版本冻结的评测世界，
结果不确定、不可重放。评测里有两套方案：确定性规则 baseline，和多步调查 Agent。这份文档说明怎么评
它们：每套方案能看到什么信息、评测集怎么造、每个指标怎么算、最近一次结果是什么，以及这些数字能说明
什么、不能说明什么。

结果那一节只保留最近一次运行，重跑就整节覆盖。其余部分写的是评测本身，不随代码改。

## 两个方案

两套方案看同一份商品事实，差别只在允许看到多少信息。这是可比性的前提：谁都不能看到别人看不到的材料。
共同输入就是商品本身：标题、描述、属性、类目、品牌、SKU、图片，以及机审已经产出的图片文字（OCR）。

**Rule baseline：只用确定性规则。** 对这份事实跑黑名单品牌、违规关键词、类目规则、图片 Logo、
OCR 关键词、风险分阈值，命中黑名单品牌这类硬规则就直接判 REJECT。规则判 PASS 记 PASS，判 REJECT 记
REJECT，判"复杂，需要进一步查"记 HUMAN_REVIEW —— 这是线上三分流的真实判定链，评测直接复用
`pra.screening`，不另写一套规则。注意线上是"复杂案交给 Agent 终裁"，评测里是"复杂案记 HUMAN_REVIEW"，
两者不是一回事。

**Agent：真实 LLM + 固定 Eval World + 工具调查。** 按证据缺口动态调工具，查商家历史、相似案例、
政策条款、图片相似度，多步推理后再下结论，同样有转人工出口。终裁必须经事实证据与 Gate 校验，
不采信模型自报的假设与置信度。

两套方案都输出 PASS / REJECT / HUMAN_REVIEW，都写进同一条记录、交给同一套指标计算，否则没法比。
记录里有决策、风险等级、风险类型、证据列表、引用的政策条款、实际调用的工具，以及成本（模型调用次数、
工具调用次数、token 数）。记录里还带一段调查轨迹供 Agent 专用指标取数：每次工具调用前后的信心变化、
是否带来新证据、是否让结论翻转。

确定性桩臂与「一次模型调用」对照臂都已删除 —— 正式评测只跑上面两套，没有确定性对照臂。

## 评测集

一条评测案包含：唯一编号、程序化变异的溯源（`lineage.seed_case_id`）、商品事实快照，以及期望答案。
期望答案不只有 PASS/REJECT，还包括风险等级、风险类型、期望证据类型、Agent 应该调用哪些工具，
这样评测才能区分"结论蒙对了但理由错了"。

- `lineage.seed_case_id` 指向种子案，用于 **RAG 语料防泄漏**：进评测集的种子案不得再进 RAG 语料，
  否则检索会命中被考的那条。这条由测试守住。
- 期望工具为空 = 没标注，不是"应该调用 0 个工具"，这类案不计入工具选择指标的分母。

合成与变异由脚本生成，产物可重复；数据集按版本存放、随代码一起入版本库。

### 已知局限

- **只有一个标注者**。真值由生成器按与评测审查员同源的规则程序化标注，没有第二个人交叉校验，
  所以高分只说明"实现和标注规则一致"，不能外推成"调查能力强"。
- **没有内容重复的案**：去重保证不存在只差商品 ID、版本号、上架时间的重复行，但标题里的核心词
  仍然跨案复用，表观多样性有限。
- **真实模型只跑过单次**，没有重复采样，它只能证明真实链路跑得通，不代表模型水平。
- **评测不再进 CI**：正式评测没有确定性桩臂，跑分需要真实 API key、有费用、结果不可重放，因此不进 CI。
- **46 条 SHOULD_ABSTAIN 没有负例**：`abstention_recall` 已删除，不再作为指标，这类"该转人工"的案
  当前没有指标覆盖。
- **种子世界覆盖有限**：种子里没有的真实先例和完整规避史查不到，多信号和对抗类案的证据充分度、
  边际证据增益会被低估，真实检索与数据库接入后要用真实运行复核。

## 指标怎么算

### 三个分母不能混读

指标按分母分成三组，引用任何一个都要说清它属于哪一组：

| 分母 | 案集 | 指标 |
|---|---|---|
| 全量 | 全部案（含真值为 HUMAN_REVIEW 的案） | `automation_coverage`、`human_review_rate` |
| AUTO_DECIDABLE | 真值是 PASS / REJECT 的案 | `accuracy`、`precision`、`wrong_auto_decision_rate` |
| 真值 REJECT | 真值是 REJECT 的案 | `recall`、`reject_unhandled` |

拿不准就交给人（abstention）：系统不硬判，输出 HUMAN_REVIEW；这是克制不是错误，也不能当普通第三分类
混进准确率。

### 固定 Eval World

正式评测里模型是真模型，工具接**固定 Eval World**：5 个工具（商品 / 图片分析 / 商家 / 案例检索 /
政策检索），数据是随版本冻结的种子数据；生产工具集里还多一个 OCR 工具，评测集从不期望它。
结果不确定、不可重放，同一案重跑不保证一致。

评测输入的图片 url 是**中性资源 ID**，不含 clean / viol / bound / logo 这类路径语义 —— 真实模型会连
url 字面一起看到，语义化路径段等同于把真值类目直接告诉它。这条不变量由测试守住。

### 主指标表

| 指标 | 它回答什么问题 | 分母 | 数据从哪来 |
|---|---|---|---|
| Accuracy 准确率 | 判对了多少 | AUTO_DECIDABLE 案；**输出转人工也算错** | 预测决策 × 期望决策 |
| Precision 精确率 | 判 REJECT 的有多少是真违规（判错会误伤商家） | 被自动判 REJECT 的案 | 同上 |
| Recall 召回率 | 真违规被自动拦下多少（漏放会损害平台） | 真值是 REJECT 的案；**转人工算未拦下**（入分母不入分子） | 同上 |
| wrong_auto_decision_rate 自动判错率 | 自动定下来的案里错的比例 | AUTO_DECIDABLE 里被自动裁决的案 | 预测决策 |
| reject_unhandled 该拒却转人工率 | 真违规有多少没被自动拒、而是安全地转给了人工 | 真值 REJECT 的案 | 预测决策 |
| human_review_rate 转人工率 / automation_coverage 自动化率 | 人工要接多少活、多少案是自动定的 | 全部案 | 预测决策 |

几条容易踩的坑：准确率的分母是 AUTO_DECIDABLE，输出转人工按错算，这比"只算自动判决的案子"更严，
是为了逼着自动化率与安全一起看；精确率与自动判错率只在自动裁决的案子里算，转人工不进它们的分母。
`recall` 与 `reject_unhandled` 的分母都是**全部真值 REJECT 案**，转人工在两者里都算"没被自动拦下"；
真值 REJECT 案被"自动拒绝 / 转人工 / 自动放行"三个互斥桶完全划分，故恒有
**`recall` + `reject_unhandled` + 漏放率 = 1** —— 看 `recall` 的缺口时必须再用 `reject_unhandled`
区分它是**安全的转人工**还是**危险的漏放**。**自动化必须和安全一起读** —— 只有方案能把复杂案里的
一部分安全地自动化（自动化率上升，同时自动判错率与 `reject_unhandled` 不恶化）时，才谈得上是价值。

### Agent 专用指标

| 指标 | 它回答什么问题 | 分母 | 数据从哪来 |
|---|---|---|---|
| Tool Selection Accuracy 工具选择准确率 | 该调的工具调了没有 | 标注了期望工具的案 | 期望工具集合 × 实际调用集合 |
| redundant_tool_rate 多余调用率 | 调了多少没必要的工具 | 标注了期望工具的案 | 实际调用集合 |
| risk_type_coverage 风险类型命中率 | 风险类型说对了多少 | 标注了期望风险类型的案 | 期望值 × 输出值 |
| risk_level_agreement 风险等级一致率 | 风险档位说对了多少 | 标注了期望风险等级的案 | 期望值 × 输出值 |
| evidence_gain_rate 有效取证率 | 工具调用里多少带来新证据 | 成功的工具调用 | 调查轨迹 |
| decision_changed_rate 结论翻转率 | 多少工具调用改变了结论 | 成功的工具调用 | 调查轨迹 |

取数规则：期望工具、期望风险类型为空的案不进分母；结论对但推理错要靠抽样人工复核，自动化只能近似。
**预算占用率不出数** —— 它不是"再补一个指标"的事：记录里没有随案冻结的预算上限，硬算只能拿当前配置
去套历史运行，那是**伪造观测**；真要做，先让预算快照随案落库。

### 成本怎么记

每次运行报模型调用次数、工具调用次数、token 数的均值、P50、P95、最大值，以及整次运行的墙钟时间。
token 总量是硬数，费用按官方价估算；估算口径以代码为准。延迟是进程内的墙钟量、不随案落库，
只在真实模型运行时才有。

### 阈值不随数据集调

外观相似度的分档、预算上限都是**工程初始值**，写在生产真正读它的那处常量里，**没有在评测数据集上
拟合过，也不会因为评测结果回改**；具体取值以代码为准。

将来真要校准生产阈值，得先把可配置点下沉到生产读常量的位置，并把阈值附近的案子补齐 —— 那是另一次
设计。同理，评测不会为了"方便观察"放宽生产预算档位。

## 这些数字能说明什么、不能说明什么

- **真实世界只代表那一次运行**：单次、单模型、非确定性，也没做提示词调优和重复采样；它不能当成
  模型固定水平。
- **生产侧的限制如实声明**：图片分析与 OCR 还是桩，装配时明确声明为"不可测"，免得把"测不出来"误判成
  "测过且没问题"；后果是生产入口对带图案件在拿到真实视觉数据源之前不会自动放行，这是已声明的缺口。
  单一商家的历史画像也不能单独作为自动下架依据，必须有本案商品的外观或文本信号佐证。
