# 商品内容治理 · 复杂风险调查 Agent —— 需求方案

> 本文只写**需求**：解决什么问题、服务谁、边界在哪、验收口径是什么。
> 怎么做（架构、状态图、Gate、工具、检索）见技术方案文档（docs/00-system-design.md）。
> 项目性质：面试作品集，核心叙事是**可控性** —— 让模型只做语义推理，让确定性代码做路由与安全。
> 正确性契约（判定三态、证据红线、禁止静默降级等底线）以仓库 AGENTS.md 为准，本文不重复。

## 1. 问题陈述

电商平台的商品审核链路中，确定性机审（黑名单、关键词、类目规则、风险分）能处理大部分明显正常
和明显违规的案件。但总有一批复杂案：文本没有硬命中、商品在库事实对不上、商家有违规前科、
案例与政策里没有可直接套用的先例。

这类案件今天的出路只有人工审核，而人工审核单价高、吞吐有限。把这类案件全量交给大模型直判则带来三个新问题：慢、贵、结论不可控
（模型可以被表面信号带节奏，且无法回答"凭什么这么判"）。

**需要的是一个嵌入现有审核链路的「复杂案件处理节点」**：接收机审分流出的复杂案，自主决定
查什么、怎么查，基于证据给出裁决；证据不足时主动转人工，而不是硬判。

## 2. 解决方案（需求视角）

系统对每条复杂案执行**调查**：提出风险假设、制定查证计划、调用取证工具收集证据、复核假设，
循环直到证据充分或预算耗尽，然后输出三分类裁决：

- **PASS**（放行）：没有任何阳性证据，且本案必需的测量维度全部覆盖、结论均为阴性；
- **REJECT**（拒绝）：有文本自证的硬命中，且有可引用的政策或先例依据；
- **HUMAN_REVIEW**（转人工）：证据不足以支撑安全的自动决策 —— 这是克制的正确行为，不是失败。

每个裁决都附带**证据链**（支撑证据 + 引用的政策条款 + 调查轨迹），使"这个商品凭什么这么判"
永远可以被回答和审计。

## 3. 用户故事

### 平台审核负责人

1. 作为平台审核负责人，我希望机审拿不准的复杂案由专门的调查节点异步处理，以便全量审核吞吐不被拖慢。
2. 作为平台审核负责人，我希望每条复杂案得到 PASS / REJECT / HUMAN_REVIEW 三种结论之一，不存在第四种含糊状态。
3. 作为平台审核负责人，我希望每个裁决附带可引用的证据链，以便任何"凭什么这么判"的追问都能在证据和轨迹中找到答案。
4. 作为平台审核负责人，我希望调查有预算上限（模型调用、工具调用、token、时间），超限自动带已有证据转人工，以便单案成本可控。
5. 作为平台审核负责人，我希望系统依赖（数据库、检索、模型）不可用时显式失败或记为失败，以便不会拿到冒充正常的空结果。
6. 作为平台审核负责人，我希望同一商品同一版本只审一次，以便重复事件不造成重复调查与重复计费。
7. 作为平台审核负责人，我希望调查成本、延迟、自动化的量级可测量，以便评估引入该节点的投入产出。

### 人工审核员

8. 作为人工审核员，我希望收到的转人工案件附带系统已收集的全部证据和调查轨迹，以便我不必重复已完成的取证。
9. 作为人工审核员，我希望只收到确实需要人判的案件（证据不足、主观判定、预算耗尽），以便我的时间花在真问题上，而不是给系统兜底偷懒。

### 商家

10. 作为商家，我希望自动拒绝必须有可引用的政策条款或先例依据，以便我不会被"模型觉得违规"拒掉。
11. 作为商家，我希望我的历史违规记录不会单独导致某个商品被自动拒绝，以便每个商品按其自身证据被对待。

### 平台法务 / 合规

12. 作为平台合规负责人，我希望命中硬规则（如黑名单品牌）的商品必须被拒绝、模型无权覆盖，以便安全红线不被概率性判断稀释。
13. 作为平台合规负责人，我希望证据不足的案件一律转人工而非猜测补齐，以便平台不承担"系统编造理由"的法律风险。

### 评审者（作品集场景）

14. 作为评审者，我希望看到确定性规则、一次模型直判、多步调查三套方案在同一批案件上的对比，以便判断调查节点的增量价值是否真实。
15. 作为评审者，我希望评测真值每条都可追溯到规则书条款，以便结论可以被复核而不是被宣称。
16. 作为评审者，我希望看到评测的已知局限被如实声明，以便区分"做过验证"和"做了但没验证"。

## 4. 边界

### 4.1 系统在链路中的位置

- 系统是**嵌入现有审核链路的复杂案件节点**，不是全量审核系统。全量初审由平台既有机审承担。
- 系统从机审分流结果的 **COMPLEX 支路**接案。仓库内置的 screening 规则引擎仅是**上游机审的替身**，
  供独立运行与评测使用；生产集成时机审结果由调用方传入。
- 系统输出终止于**结构化裁决 + 证据链落库**。HUMAN_REVIEW 是终态输出；
  人工裁决及其向案例库、政策库、评测集的回流属于**下游系统职责，在边界外**。

### 4.2 输入与输出契约（需求级）

- **输入**：商品事实快照（标题、描述、属性、类目、品牌、SKU）、商家标识、事件类型、机审已产出的结果。
- **输出**：三分类裁决、风险等级、风险类型、置信相关展示量、证据链（证据 + 引用 + 调查轨迹）。
- 风险等级与置信类展示量只用于展示、人工队列排序与统计，**不作为判定输入**。

### 4.3 业务范围：只做 IP 仿冒与规避审核

当前阶段只承诺一个核心场景：**疑似品牌仿冒（IP 风险）+ 规避审核行为模式**。
风险类型受控词表只保留两个值：`POTENTIAL_IP_RISK`、`EVASION_PATTERN`。

选这个场景的四条理由（需求论证，与具体方案无关）：

1. 仿冒卖家与规避行为高度共现 —— 同一对手的两条互补证据通道（listing 外观证据 + 商家行为证据）；
2. 它压中审核决策最本质的认识论不对称：变形词可文本自证，商家画像永远不能自证 ——
   这正是"可控性"叙事最有存在必要的地方；
3. 它是对抗性场景，静态规则注定腐烂 —— 调查型节点的增量价值在这里最大；
4. 所需证据全部在内部系统（商品库、商家库、政策库、案例库）可得，调查闭环不依赖外部事实验证。

**虚假宣传（FALSE_CLAIM）与商品字段冲突（FIELD_CONFLICT）本阶段不做**，从词表、数据、
政策库元数据中整体移除；前者缺外部事实验证源导致闭环不成立，后者太接近确定性规则、
调查增量趋近于零。两者进入 §7 roadmap。

## 5. 验收口径（评测需求）

验收的核心问题：**同一批复杂案上，确定性规则、一次模型直判、多步调查三套做法各自解决了什么。**

### 5.1 三臂对比

- 三套方案（rule / single / agent）跑同一份评测集、进同一套指标计算；
- 材料边界钉死：rule 与 single 只看案件快照，只有 agent 允许调用工具取得快照之外的证据；
- 正式评测只跑真实模型，需要 API key、有费用、结果不可重放，不进 CI。

### 5.2 真值：构造即标签，零人工标注

- 评测集由生成器合成；生成器造案时显式输出**埋点清单**（本案植入的语义事实，Agent 不可见）；
- **独立打标函数**（与生成器分离的第二次实现）按冻结的规则书，从埋点清单推导标准答案
  （期望裁决、风险类型、期望证据类型、期望工具、应引政策）；
- 规则书（判定口径）在标注前宣布冻结；规则书变更时，标签口径同步变更；
- 打标函数配单测（规则书典型情形），标签分布不变量与矛盾检测全自动化。

### 5.3 判卷与交叉检查

- 判卷是**确定性代码比对**，不使用模型当裁判；
- **独立模型交叉检查（审计模式）**：一个与被测模型不同源的模型，只看规则书 + 案例文本
  （看不到埋点清单），独立给出裁决；与标准答案比对后：
  - 一致 → 进入头条指标统计；
  - 分歧 → 进入疑问篮子：从头条指标分母剔除、单独公开、**不做自动改标**；
- 头条指标采用 selective prediction 口径：coverage（自动决策占比）、selective risk
  （自动决策错误率）、错误拒绝率（不对称成本：误拒 ≫ 多余转人工）；
- 第二层（无真值检查）：蜕变测试、pass^k 重复运行一致性、过程断言（预算守住、引用可解析、
  无静默降级）。

### 5.4 已知局限（必须如实声明）

评测报告必须显式声明：真值由受控构造产生、未经独立人工复核，残余风险为规则书解释偏差；
疑问篮子中的分歧案例未经裁决；生成器能造的风险模式受设计者想象力限制，合成分布不等于真实分布。

### 5.5 工程指标（只定义方法，不预设数值）

- 单案调查成本、单案延迟分布、每案模型调用次数分布，三项指标必须在真实评测中实测；
- 目标值的设定方法：以首跑实测分布为基线校准，并写明校准依据；不预先拍数字；
- 成本口径以人工审核成本为参照（§1），调查节点成本应显著低于人工。

## 6. 需求级实施决策

正确性契约（判定三态、终裁约束、硬规则、证据红线、预算语义、评测红线等不可覆盖的底线）
以仓库 AGENTS.md 为唯一事实源，本文不重复。以下为仅属需求层的约定：

- 评测、政策库元数据、决策输出共用同一套风险类型词表（当前 2 个值，见 §4.3）。
- 模块划分、框架选型、流程编排属于技术方案文档，不在本文承诺范围内。

## 7. Out of Scope

- 虚假宣传、字段冲突两类场景（roadmap：待引入外部事实验证源 / 明确与机审边界后再议）；
- 人工审核工作台、人工裁决及其向案例库/政策库/评测集的回流（下游系统职责）；
- 全量 Agent 审核（定位是复杂案件节点，不是全量审核系统）；
- 上游机审本身的能力建设（内置 screening 仅为替身）；
- 真实业务方接入与上线（项目性质为面试作品集）；
- 评测真值的人工标注与人工审计（本阶段明确选择零人工，局限见 §5.4）。
