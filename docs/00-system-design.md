# 商品内容治理 · 复杂风险调查 Agent —— 设计与判定口径

平台每天要过大量商品。机审能挡掉大部分明显违规，但总有一批案子说不准：标题干净、图片可疑、
商家还有前科。这个项目专门处理这批案子 —— 它自己决定去查什么，查完给出三种结论：
**放行（PASS）、拒绝（REJECT）、交给人（HUMAN_REVIEW）**。

这份文档写的是设计与判定口径：系统怎么分工、调查怎么走、结论怎么定、哪些红线不能碰、哪些事明确不做。
它不记录"现在写到哪一步"（那是 [README](../README.md) 与记忆台账的事），也不放评测数字
（那是 [评测文档](02-evaluation.md) 的事）。所以除非项目的流程或功能本身变了，这份文档不需要改。

## 0. 机审与 Agent 的分工

传统机审负责**确定性异常**：黑名单、关键词、敏感词、类目规则、Logo 检测、OCR、风险分模型。
这些判断快、便宜、可复现，适合全量过一遍。

Agent 负责另一类案子：**开放、依赖上下文、要把多个来源的证据交叉起来才能判**的复杂风险。
它的产出同样是三种结论，证据不够时主动转人工 —— 转人工是克制的正确行为，不是失败。

```
商品上架 / 改标题 / 改属性 / 改图片
   ↓
规则 + 传统模型初筛（同步、快、便宜，全量过）
   ↓
三分流：明确正常 / 明确违规 / 复杂低置信
   ↓
复杂低置信 → 复杂风险调查 Agent（异步、预算受限）
   ↓
PASS / REJECT / HUMAN_REVIEW
   ↓
HUMAN_REVIEW → 人工裁决 → 回流案例库 + 政策库 + 评测集
```

一句话原则：**能用规则解决的，不交给模型；Agent 不是全量审核系统，而是机审链路里的
「复杂案件处理节点」。**

## 1. 整体架构：同步初筛 + 异步调查

### 1.1 为什么分两段

- 规则和传统模型是**同步确定性**链路：毫秒到秒级、可并行、不烧 token。
- Agent 是**慢、贵、结果带不确定性**的链路，只处理分流出来的复杂案（设计假设：不到全量的 15%），
  异步消费 + 预算限制 + 失败重试。

这样 Agent 的引入**不会拖慢全量审核吞吐**，只是给复杂案追加一个"调查节点"。

### 1.2 每一层干什么

| 层 | 职责 | 关键点 |
|---|---|---|
| 接入 | 接收商品上架 / 变更事件 | 现在是同步 HTTP 入口；消息队列是将来并发上来之后的扩展位，现在不引入 |
| 同步机审 | 跑规则与传统模型，产出信号、风险分 | 确定性、全量、低延迟 |
| 分流 | 把结果分三堆：明确正常 / 明确违规 / 复杂 | **确定性规则，不是模型**；硬规则高分直接拒、无信号低分直接放、中间带进复杂队列 |
| 复杂调查 | 对复杂案做多步取证 | 异步 worker，状态图编排，预算受限 |
| 决策与人工 | 输出结论并闭环 | 自动结论落库并通知商家；转人工进审核工作台，人工裁决回流成案例与政策 |

技术选型上只需要记住两条：**调查用状态图编排**（显式状态 + 条件边 + 检查点，正好是这个循环需要的骨架），
**检索用关键词 + 向量混合**。具体用了哪些库、哪个版本，以仓库配置为准，本文不镜像。

## 2. 案件模型：输入是事实，输出是裁决 + 证据链

一条案件就是一次审核的完整上下文。输入是**商品事实快照**：标题、描述、属性、类目、品牌、SKU、图片，
以及机审已经产出的图片文字（OCR）和机审信号。机审做过什么、结论是什么要一起带进来，
作为调查的**起点信息**，避免 Agent 重复劳动。

输出是**结构化裁决 + 证据链**：三分类结论、风险等级、风险类型、安全信心、支撑结论的证据、
引用的政策条款，加上这次调查的过程轨迹。证据链是核心 —— 以后有人问"这个商品凭什么这么判"，
答案必须在证据和假设轨迹里找得到，不能只存在于模型的上下文里。

两条口径不变：

- 支撑判定的证据必须带**可追溯引用**（引用到具体政策条款或具体先例），不可引用的材料撑不起拒绝。
- 风险类型走**受控词表**（见 §7.3），这样评测标签、政策库元数据、决策输出三者才能用同一套词表做统计。

字段名、字段清单与序列化形态一律以代码为准，本文只写语义。

## 3. Agent 的状态：显式、可序列化、可恢复

Agent 的状态必须是显式的、能序列化的、能持久化并恢复的，而不是藏在模型的对话上下文里。
这是"工程化的 Agent"和"一个 prompt 循环"的分水岭。

### 3.1 设计要点

1. **假设是状态的核心**：Agent 不是分类器，是假设验证器。每条假设有自己的验证状态，调查过程可解释。
2. **每步都持久化**：状态由状态图框架的检查点逐步落盘，"崩溃可恢复、断点续跑"以持久化为前提；
   评测里的重放也靠它。
3. **预算是状态的硬字段**：进入节点之前先检查预算，超限直接路由到转人工止损。
4. **结论依据与过程审计分开**：证据是前者，工具调用历史是后者，两者都进轨迹。
5. **图的终态只有一个**：收敛即终态。`PASS / REJECT / HUMAN_REVIEW` 是最终裁决的取值，不是图的状态；
   预算耗尽、工具失败、降级这些都通过裁决上的改判记录留痕，不另开状态。

### 3.2 状态契约

- **只装调查记忆与图内控制通道**：商品事实、假设、证据、待查问题、工具调用历史、预算、决策。
  运行标识与运行状态不进状态（运行状态在库里）。
- **证据一旦收集不可篡改**：证据合并遇到重复按去重键丢弃新增，绝不覆盖；工具调用历史和失败记录只追加。
- **不累积对话历史**：每个模型节点都从状态重新组装 prompt，一次调用内部的对话只活在这次调用里 ——
  这样状态可序列化、token 可预算、重放可确定。
- **边界由入参结构约束**：假设条数、待查队列长度、单轮计划里的工具数都由 schema 限定。
- **判定不读模型量**：两道 Gate 与收敛判定都不消费模型产出的假设状态与概率（见 §7.2）。
- **模型步失败怎么降级**：结构化输出校验失败先自动重试一次；仍失败则该节点返回降级结果并打标记，
  之后不再调用模型，统一按"证据不足"路由到决策，由确定性收口产出 `HUMAN_REVIEW`（硬规则命中除外）。
- **假设的生命周期**：待验证 → 被支持 / 被否定 / 查过但未能证实也未能证伪。最后一种要和"还没查"分开 ——
  它只是说这条线索查完没结论。假设状态**只用来引导调查和留痕**，最终裁决由证据事实决定，不由假设状态推导。
  假设在入口生成一次，运行中新冒出来的由复核节点追加。

## 4. 调查循环与图的分工

### 4.1 循环本身（与框架无关）

```
观察（读商品事实 + 已有信号 + 已有证据）
   ↓
提假设（生成 / 更新风险假设）
   ↓
定计划（验证哪条假设？还缺什么证据？）
   ↓
行动（动态挑工具并调用）
   ↓
观察（读工具结果，合并进证据）
   ↓
复核（依据新证据更新假设状态）
   ↓
决策（证据够 → 出结论；不够 → 回到计划，或转人工）
```

### 4.2 谁做什么：这是本项目最重要的工程决策

| 步骤 | 谁来做 | 为什么 |
|---|---|---|
| 图编排、条件边路由、预算记账 | 状态图 + 确定性 Python 路由函数 | 可靠、可测、成本可控 |
| 工具执行、结果反序列化、证据去重合并 | 确定性代码 | 不浪费 token |
| 提假设、定计划、复核证据、给决策提案 | 模型节点（结构化 JSON + schema 校验） | 这些需要语义推理 |
| 硬规则兜底（黑名单必拒） | 决策前的确定性收口 | 安全红线 |
| 状态持久化、恢复、重放 | 状态图检查点（后端可替换） | 重放确定 + 崩溃恢复 |

选现成的状态图框架（LangGraph）而不是自研循环，是因为它的核心模型 —— 显式状态 + 图 + 检查点 + 条件边 ——
正好就是这个循环需要的骨架，可以直接省掉自写状态机、持久化和重放的重复劳动。但框架**只负责编排骨架**，
下面这些仍是自研：预算护栏、硬规则兜底、证据去重、工具参数 schema、决策收口、轨迹落库。

> 关键边界一句话：**让模型做语义推理（节点内部），让确定性代码做路由与安全（条件边 + 护栏）。**
> 如果整张图交给模型决定怎么走，就会同时得到成本失控、不可控、不可测三个问题。

### 4.3 为什么是动态挑工具，而不是固定流水线

固定 `A→B→C` 会对每个案子无差别地调所有工具，纯属浪费（商品字段没冲突时没必要调 OCR）。
动态挑工具的依据是：**当前最值得验证的假设，需要哪条证据？** 由计划节点决定、条件边路由过去。
比如 OCR 读到 "100% Polyester" 而标题写"真丝"，那就该优先调商品工具做字段交叉，而不是再跑一遍图片分析。

这是 Agent 相对"固定工作流"的核心增量，也是评测里工具选择指标的来源。

### 4.4 一次调查走查（常见硬案：复古运动鞋）

| 轮次 | 干什么 | 结果 |
|---|---|---|
| 0 | 读商品事实与机审信号：全部放行、品牌为空、没有品牌词 | 立起初始假设 |
| 1 | 最该查的是：外观是否对应某品牌 | 调图片分析工具 → 相似度 0.91，成为证据 |
| 1 | 复核 | 相关假设被支持，另一条被削弱 |
| 2 | 要确认商品字段与商家历史 | 调商品工具（品牌确实为空）+ 商家工具（23 次相似上架 / 5 次下架 / 3 次改标题重上） |
| 2 | 复核 | 规避行为这条假设被支持 |
| 3 | 需要先例与政策支撑 | 查案例库（有高度相似先例，历史结论是拒绝）+ 查政策库（支持高风险转人工） |
| 3 | 复核 | 证据链完整，收敛 |
| 4 | 决策 | 证据充分，但"仿冒"是主观判定 → 转人工（高风险） |

注意最后一步：Agent 的价值不只是"自动判掉"，更在于**知道什么时候证据够了、什么时候该人介入**。

### 4.5 各节点的契约要点

| 节点 | 要点 |
|---|---|
| 提假设 | 入口执行一次；读商品事实与机审信号，产出初始假设与初始调查队列 |
| 定计划 | 每轮说清"下一步验证哪条假设、调哪个工具、为什么"；没有值得做的动作就直接转决策 |
| 工具 | 确定性执行：按工具名 + 参数分发，反序列化结果、去重合并证据；单批调用按上限截断 |
| 复核 | 依据新证据更新假设状态、必要时追加假设；证据不够且预算没超就回计划，否则转决策 |
| 决策 | 模型只给**提案**，随后由确定性收口按 §7.2 的顺序定稿，改判与原因记在裁决上 |

防重复动作：计划节点反复提议同一个调用时，第二次即清空计划并视同"可以收尾"，不存在空转烧预算的死循环。

## 5. 工具：六个，各自回答一个问题

每个工具都要能回答"审核员为什么需要这条信息"，不为数量堆工具。

| 工具 | 回答什么 |
|---|---|
| 商品工具 | 这个商品的事实是什么？尤其品牌字段是不是真的空、字段之间有没有冲突 |
| 图片分析工具 | 商品外观与某个品牌或违禁视觉有多像？ |
| OCR 工具 | 图片里到底写了什么？用来和标题、描述交叉验证 |
| 商家工具 | 这个商家是不是在系统性地做类似的事？ |
| 案例检索工具 | 有没有类似且已有人工裁决的先例？结论是什么？ |
| 政策检索工具 | 当前有效的政策对这类情况怎么说？ |

一句话记住各自的不可替代性：商品工具是**事实锚点**，图片分析补的是**规则覆盖不到的外观证据缺口**，
OCR 用来**发现图文冲突**，商家工具给的是**行为模式**，案例工具给**先例参照**，政策工具给**判定依据**。

生产工具集就是这六个。评测世界用其中五个（不含 OCR），评测集从不期望它 —— 评测口径见评测文档。

工具抽象上只有两条：计划节点只输出"调哪个工具、带什么参数"，由分发器按名字调度并对参数做强校验；
**不做 MCP** —— 六个工具都是内部服务，统一接口加注册表就够了。等到要接外部、第三方或跨语言的工具时，
标准化的价值才显现，那时候再引入。

数据来源按世界分：默认离线路径与评测世界读**固定种子数据**（这是评测可重放的前提，CI 不连外部数据源）；
生产入口读真库与真实检索。**真链路不可用时必须显式失败并记为失败，不静默回退成种子数据** ——
这是"禁止静默降级"的硬约束（见 §8.2）。

## 6. 两类知识库（RAG）

### 6.1 政策库与案例库，作用不同

| 知识库 | 装什么 | 在什么时候用 |
|---|---|---|
| 政策库 | 审核规则、平台政策、违规判定标准（带版本与生效日期） | 调查中给出"当前适用的政策依据" |
| 案例库 | 历史人工审核案例（商品、证据、最终裁决、依据政策） | 调查中给出"相似案件先例"作为参照 |

要澄清一点：**RAG 不是让模型背规则的**（那是规则引擎的活），而是在调查过程中把政策依据和先例依据
**作为证据注入**，让结论有据可依、可引用、可审计。

### 6.2 怎么检索

- **混合召回**：关键词（BM25）加向量相似度，融合后取前 K 条。
- **元数据过滤**：按类目、风险类型、政策是否在有效期内过滤，避免召回到过期政策或不相关类目的案例。
  两路实现的过滤**语义必须逐条等价** —— 向量路把过滤下推到库里，关键词路只能在 Python 候选集上过滤，
  改一侧必须同步另一侧，并由测试锁死，否则漏召回只在带过滤时才暴露。
- **融合与截断**：两路结果用 RRF 融合后截断，控制注入上下文的量；不做重排序。
- **引用格式**：政策的引用要带政策编号、版本、条款原文；案例的引用要带案例编号与结论。
  进了证据链就必须能追溯回原始条款或原始案例。

### 6.3 分数与模式的口径（几条容易搞错的红线）

- **检索分不是语义相似度**。它是后端定义的检索分：关键词路是无界的原始分，向量路是距离的单调函数，
  混合路是 RRF 分，三者**量纲互不可比**。任何场合都不得把它叫成"相似度"。
- **不换算量纲、不设取值域约束**：排名只依赖单调性，换算没有收益；这个分往下只用于渲染证据行和落库审计，
  **不参与任何 Gate 判定** —— Gate 对案例与政策证据只判"有没有可引用的依据"，不读分值。
  用 min-max 之类把分数拉平属于伪造，不做。
- **图片外观相似度是另一类证据**，和检索分不是一回事。
- **单路模式是检索侧能力，不是评测配置面**：评测只跑生产口径的混合模式，不会在
  "评测 → Agent → 工具 → 检索"这条链上贯一条模式开关；要调试单路模式走独立入口。
- **建库必须显式指定余弦度量**：用错度量会让"像不像"的整体间距语义偏移，而且**不报错**，只是排名和分数一起失真。
- **写入与元数据**：同一条记录不会被覆盖，写入要先删后加；元数据的形状变了必须换集合名，
  否则旧库被原样复用，新过滤条件会**静默零命中**。
- **取回多少就是多少**：前 K 条不保证真的返回 K 条；检索真失败（服务不可达、集合不存在、编码失败）
  直接上抛，不另补一套检索兜底。
- **分词与索引各自持有**：不替换第三方库的全局符号，各检索器实例互不共享状态，并发下互不干扰。
- **不为测试引入假编码器**：生产、测试、回归、评测用同一个真语义模型，避免"测试里像、线上不像"。
- **内存版向量库对 id、维度之类的约束比真服务端宽松**，缺陷可能在单测全绿的情况下潜伏，
  只在真服务端暴露 —— 真服务端的集成用例不能省；反过来说，不装检索依赖的环境里
  这些用例整体跳过，不能声称"CI 覆盖了向量库"。

### 6.4 向量库选型与知识回流

语料是小语料，用 ChromaDB 就够了，明确不上 Elasticsearch、Milvus、知识图谱这类重型方案，降低工程复杂度。
图片向量单独存，和文本向量库分开。

**知识回流是"越用越准"的机制**：人工裁决结果沉淀成新案例、重新向量化后进案例库；政策更新则版本化，
生效后替换检索范围。系统的闭环在这里合上。

## 7. 三分类决策机制

### 7.1 先分清两个量，再看三分类

转人工（abstention）的本质**不是"置信度低于阈值就交人"，而是"证据是否足以支撑一次安全的自动决策"**。
为此有两个必须分开的量：

| 概念 | 一句话定义 | 用途 |
|---|---|---|
| 安全信心（`decision_confidence`） | 对"这次自动决策不放人工"的把握 —— **是安全门槛量，不是模型判"是否违规"的概率** | 决定能不能自动判；它不回答"风险有多高" |
| 风险等级与风险强度（`risk_level` 等） | 风险本身的高低与强度 | **只用于展示、人工队列排序、统计**；不参与路由，也不参与判定 |

三分类的语义：

| 决策 | 含义 | 触发条件概要（完整规则见 §7.2） |
|---|---|---|
| PASS | 放行 | 没有任何维度匹配的阳性证据；没有规则侧阳性；本案必需的测量维度全覆盖且都是阴性；没有关键工具失败、没有关键矛盾 |
| REJECT | 违规，拒绝上架 | 有足以授权的硬阳性；有带引用的可引用依据；安全信心达标；没有关键矛盾 |
| HUMAN_REVIEW | 转人工 | 两道 Gate 都没过，或命中弃权清单 |

### 7.2 决策规则：模型只提案，确定性 Gate 收口

决策分两层：**模型给提案，确定性 Gate 做最终校验**。收口按下面的顺序执行，任何一步不满足就改写成
`HUMAN_REVIEW`，并把改判原因记在裁决上：

1. **硬规则优先，模型不可覆盖**：调查中命中黑名单品牌（R-101）这类硬规则或硬违规，强制 `REJECT`；
   哪怕模型说 PASS，也以命中为准 —— 这是防漏放。
2. **用事实重算安全信心**，不采信模型自报的数字。
3. **弃权清单**：下列任一成立就转人工（哪怕提案是 PASS 或 REJECT）：
   - 本案必需的维度**本环境可测却没测**（属于可补救的取证缺口，先回环补测）；
   - 必需维度**在本环境测不了**（重跑也没用，不回环）；
   - 阳性不足以自动拒绝（只有弱信号、只有商家画像、或者没有可引用依据）；
   - 关键证据互相矛盾；
   - 关键工具失败导致证据拿不到；
   - 预算耗尽 —— 带上已经查到的证据转人工；
   - 任何一步降级。
4. **提案过不了对应的 Gate**：PASS 提案过不了 PASS Gate，或 REJECT 提案过不了 REJECT Gate。

**REJECT Gate** —— 可以自动拒绝，当且仅当下面全部满足：

- 有**足以授权自动拒绝的硬阳性**：本商品直接测到的强外观相似或 Logo；或者商家行为脏**且本案有外观信号
  佐证**；或者命中平台规则里的规避词（R-302，文本自证）。
- 有**可引用依据**：至少一条带引用的政策条款或高度相似的先例证据 —— 这是防误伤，拒审同样是资损和商誉损失。
- **安全信心达标**：门槛见 §7.6。
- **没有关键矛盾**（比如相似度极高但商家历史干净）。

两条容易被放宽的红线，必须写清楚：

- **弱相似不算硬阳性**，单独不足以自动拒绝 —— 它要和"商品事实"维度交叉；交叉不了就该转人工。
- **只有商家历史脏，也不授权自动拒绝**。商家画像是针对该商家的统计，不能当成这一个商品违规的确证；
  必须有本案商品的外观或文本确证。品牌词命中（R-102）同理：**它只阻塞放行，不授权拒绝**。

**PASS Gate** —— 可以自动放行，当且仅当下面全部满足：

- 没有任何维度匹配的**阳性证据**（含仅商家画像这种）；
- 没有**规则侧阳性**（品牌词、规避词命中一律阻塞放行）；
- 本案必需的测量维度**全部覆盖，且结论是阴性**；
- 没有关键工具失败、没有关键矛盾。

这里的三态要分清：证据承载"测过（含**阴性**结论）"这一类；"没测"和"本环境测不了"**不是证据**，
由 Gate 用"必需维度 × 证据有没有 × 环境能不能测"推导出来。**绝不为"缺席"造证据** ——
这样才能把"证明没风险"（可以放行）和"没查到风险"（应当转人工）区分开。

两条结构性约定：**本案需要测哪些维度，由案件的客观事实决定**（商品事实、商家、文本恒必需，带图案件
多一个外观维度），**不由模型的计划或假设决定**，否则判定会随模型的计划波动；**两道 Gate 都不读模型生成量**
（假设、概率、提案里自报的置信度都不读），提案只决定走哪道 Gate。

### 7.3 风险类型受控词表

```
POTENTIAL_IP_RISK     疑似 IP / 品牌模仿
EVASION_PATTERN       规避审核行为模式
FALSE_CLAIM           虚假 / 无依据宣传
FIELD_CONFLICT        商品字段信息冲突
```

评测集的标签、政策库的元数据、决策输出三者共用这一套词表，才能做召回和精确率的统计。

### 7.4 安全信心是怎么算出来的

安全信心不是一个模型拍脑袋的数字，也不是"违规概率"，而是一个**由事实算出来的确定性函数**，
可解释、可单测。它只吃四类事实：必需维度的覆盖比例、已覆盖维度的决定性证据强度、有没有可引用依据、
有没有关键矛盾。**它不读模型产出的假设与概率。**

它只回答"如果自动判，判错的风险够不够低"。**这个门槛只约束自动拒绝那一侧**；放行侧由 PASS Gate 说了算，
不会因为"风险信心低"就转人工 —— 干净商品风险低是正常状态，不是转人工的理由。

### 7.5 风险等级不参与判定

风险等级只用于展示、人工队列排序、审核优先级与统计，**不作路由输入，也不作改判输入**，避免把展示口径
变成判定逻辑。典型反例：**高风险 + 证据不足 → 转人工**，而不是高风险就直接拒绝。风险高不等于可以自动判。

### 7.6 阈值与常量

外观相似度的三档分界（不算证据 / 普通证据 / 强证据）、自动拒绝的安全门槛、预算上限，都是**工程初始值**，
写在代码常量里，并且**没有在评测数据集上拟合过**，也不会因为评测结果回改。

具体取值以代码为准。为什么不在数据集上调阈值、以及评测侧曾经有过的阈值扫描工具为什么被删掉，
评测文档的「阈值不随数据集调」一节讲清楚了。将来真要校准生产阈值，得先把可配置点放到生产实际读常量的位置，
并把中间相似度段的案子补齐，那是另一次设计。

## 8. 预算护栏、安全护栏与终止性

### 8.1 预算：是保护上界，不是目标

四组上限 —— 模型调用次数、工具调用次数、token、执行时间 —— 都是**保护性的上界**。
正常案件的实际用量应当**明显低于上限**，余量是留给结构化输出校验失败重试、工具失败恢复和防无限循环的。

| 超了哪个 | 怎么办 |
|---|---|
| 模型调用次数 / 工具调用次数 | 停止调查 → 带上已收集的部分证据转人工；工具节点同一批调用也按上限截断 |
| token | 压缩上下文，或停止 |
| 执行时间 | 超时 → 转人工 |

- 检查发生在**每次进入节点之前**（条件边里的确定性代码），不是"跑完才发现超了"。
- 上限可以在**生产装配层**配置。
- 超限的语义是：**调查成本已超出可接受范围，证据又不足以自动判，转人工最稳妥** —— 这是正确的业务行为，
  不是失败。
- **评测不为跑分放宽档位**：真实模型臂与桩臂跑的是同一套生产上限。预算够不够用本身就是被测行为；
  如果真实模型因为调用次数或执行时间撞限而转人工，那是当前预算语义的正常结果，不是评测缺陷，
  也不该靠加一个"评测专用上限"绕开。

### 8.2 安全与业务护栏

1. **硬规则不可被模型覆盖**（黑名单、硬违禁）→ 防漏放。
2. **自动拒绝必须有可引用依据** → 防误伤商家。
3. **单一来源的商家历史画像不得单独构成自动拒绝依据**，必须有本案商品的外观或文本确证。
4. **个人信息**：工具返回给模型之前先脱敏（商家联系方式之类），模型输出不落地敏感字段。
5. **决策可审计**：每个决策都带完整证据、假设轨迹与工具调用历史，能回溯到"哪个工具给的哪条证据
   导致了这条结论"。
6. **幂等**：同一商品同一版本只审一次，防止重复消费导致重复计费。
7. **禁止静默降级与静默失配**：依赖、检索或数据不可用时显式失败或记为失败，不得返回空结果冒充正常；
   数据契约发生不兼容变更时，新旧数据不得静默混用。

### 8.3 一定停得下来

- 图里**唯一的回环**是「计划 → 工具 → 复核 → 计划」；决策节点没有出边。离开回环只有三个出口：
  收敛、计划侧主动收尾、预算超限。
- 每一轮至少消耗 1 次计划的模型调用 + 1 次复核的模型调用，所以**由模型调用上限可以直接推出回环轮数的上界**
  （实际因为早停更少）。
- 空转也被堵死：计划反复提同一个动作，第二次就清空并视同收尾；工具只有六个，加上调用上限兜底；
  任何节点一步降级就短路进决策。
- 路由、预算、收敛、Gate **全是纯函数**（无随机、无模型）—— 同一个状态必定走向同一个后继，
  不存在"同状态走不同分支"的非确定性死循环。

## 9. 数据怎么落（不镜像表结构）

表的划分口径是三类：**商品事实**（商品、SKU、图片）、**商家画像与行为事件**、
**案件与运行轨迹**（案件、运行、轨迹、证据、结果）。有一条去重原则：商品图片表不存 OCR 文本、也不存向量
—— OCR 归 OCR 工具，向量归向量库，同一个事实不在两处存。

落库约定：主键统一用雪花号，版本字段做乐观锁，状态字段加索引，半结构化数据用 JSON 列；
迁移是手写的 SQL，模型校验与序列化交给 Pydantic。字段与建表语句以迁移文件和 ORM 映射为准。

**Redis 与消息队列现在不引入**：核心闭环不依赖它们（可选项不能成为默认路径的前置条件）。
真出现并发与异步需求时，它们的落点是幂等去重、限流、worker 抢占案件的分布式锁、热点缓存，
以及请求投递、复杂案投递、人工裁决回流这三个主题加重试与死信。

## 10. 观测与记账

观测分四层，各管一段，互不替代：

| 层 | 记什么 | 落在哪 |
|---|---|---|
| Agent 内部轨迹 | 每一步的工具名、参数、结果、token、耗时 | 落库，这是业务审计的真相所在 |
| 模型调用级 | 每次调用的 prompt、输出、token、成本 | Langfuse |
| 链路级 | 一个请求从接入到决策的全链路 | 链路追踪（OpenTelemetry 一类） |
| 业务指标 | 决策分布、转人工率、自动化率、各风险类型占比 | 指标表 / Prometheus |

**为什么要落库**：可复现 —— 评测重放、回归、申诉调查（"这个商品为什么被拒"）都要靠它；
成本能算到每一步。这是工程化 Agent 和调 API 的 Demo 的本质区别。

记账口径有一条不能破：**桩路径下 token 为 0、没有费用、耗时约等于 0 是真实情况**（没有真实模型调用），
**绝不填估算值上去**；真实 token 与耗时只出现在走真实模型的路径。两个世界的数字不得混算，也不得互相暗示。

观测组件缺凭据时降级为全空操作，不联网、不阻塞主流程 —— 这条只约束观测，它不影响主链路的真实性声明。

## 11. 评测集设计（口径；怎么做与数字见评测文档）

评测要回答的是同一个问题：**同一批案子，规则、一次模型调用、多步 Agent 三种做法各自解决了什么。**
数据集本身的设计口径有三条：

1. **期望标签不只有对错**。每条案子的标签包含期望决策、风险类型、风险等级、期望证据类型、
   期望调用的工具、应引用的政策。只有这样才能区分"结论蒙对了但理由错了"。
2. **标签里的证据阈值必须和运行时读的阈值口径一致**，阈值改了要同步修标签。
3. **评测集按场景分层**（明确正常 / 明确违规 / 边界 / 多信号组合 / 对抗规避），比例与规模、
   构造方法与已知局限都在评测文档里，本文不重复。

三套方案跑同一份数据、进同一套指标计算，否则没有可比性；Agent 一侧支持确定性重放
（工具返回固定结果），保证同一案重跑逐字节一致。

## 12. 三套方案怎么对比

### 12.0 公平性前提：三套方案看同一份基础输入

为避免"各方案看到的材料不一样"这种作弊质疑，三套方案在**同一条案子上共享同一份基础输入**：

```
基础输入 = 商品事实快照：
  标题 / 描述 / 属性 / 类目 / 品牌 / SKU / 图片 / 机审已产出的图片文字 / 机审信号
```

差别只在**谁允许用这份输入之外的信息**：

- **Rule**：只对基础输入跑确定性规则（可以用机审产出的 OCR 文本做关键词）。
- **一次模型调用**：把基础输入一次性全给模型，一次调用直接输出决策 JSON。
- **Agent**：允许按证据缺口**动态调查**，通过工具和检索拿到基础输入之外的证据
  （商家历史、案例库、政策库等）。

### 12.1 Baseline 1：规则引擎

对基础输入跑纯确定性规则：黑名单、关键词、敏感词、类目规则、Logo 检测、OCR 关键词、风险分阈值。
输出直接复用线上三分流：判放行记 PASS、判拒绝记 REJECT、判"复杂，需要进一步查"记 **HUMAN_REVIEW**。

注意口径差异：**线上复杂案是交给 Agent 终裁，评测里是交给人工** —— 评测语义是"没有 Agent 的时候，
复杂案只能人工"，两者不是一回事，报告必须写明。

特点是快、零模型成本、确定性，但处理不了需要多源交叉验证、依赖上下文的复杂案。

### 12.2 Baseline 2：一次模型调用

把全部基础输入加少量背景提示一次性交给模型，直接输出结构化决策 JSON。
**刻意不给商家历史、案例库、政策库** —— 那些正是 Agent 靠工具查出来的证据，先塞给它就等于作弊。
模型自报的信心分低于门槛时转人工，所以这套方案也有 HUMAN_REVIEW 语义。

评测里它**恒定是"基础输入原样"一种形态**；曾经用来对照的"预塞政策与先例文本"变体已经删掉（见 §13.4）。

### 12.3 System 3：Agent + 工具 + 检索

完整循环：提假设 → 定计划 → 动态挑工具 → 多源取证（含检索）→ 复核证据 → 三分类决策。

### 12.4 要证明的结论（方向，不虚构数据）

| 案件类型 | 规则 | 一次模型调用 | Agent |
|---|---|---|---|
| 明确正常 / 明确违规 | 快且准 | 准 | 准，但没必要，成本高 |
| 边界 / 单个弱信号 | 容易误判 | 不稳定、证据不足 | 多步取证后能判 |
| 多信号组合 | 没法交叉验证 | 缺证据 | 能交叉验证 |
| 对抗 / 规避（难例） | 直接漏过 | 输入里根本没有信号 | 靠调查取证 |

结论落点是：**Agent 的增量价值集中在"必须多步取证才能拿到决策证据"的案子上**；
对确定性案件，Agent 反而是过度设计 —— 这正是它只做复杂案件节点、不做全量的原因。

## 13. 难例基准

这是最重要的 benchmark，专门用来证明 Agent 的必要性。

### 13.1 什么算难例（满足任意一条）

1. **规则判不了或容易判错**：没有硬规则命中，但确实存在风险。
2. **一次模型调用证据不足或不稳定**：要下结论必须用到输入里**不存在**的信息。
3. **Agent 多步调查能拿到额外证据**：调工具能明显改变结论。

### 13.2 怎么造

四条来源：人工构造对抗样本（核心是品牌模仿与规避，比如没有 Logo、没有品牌词但外观高度相似、
商家还有违规史）；把历史人工裁决案脱敏改写；对模板做字段变异制造边界（改相似度、改商家历史、
制造图文冲突，用固定随机种子保证可重复）；逐条人工标注期望决策、证据、政策与期望工具。
具体做法、标注流程与已知局限见评测文档。

### 13.3 典型形态

| 子类型 | 例子 | Agent 的增量 |
|---|---|---|
| 品牌模仿 / 规避 | 复古运动鞋 + 无品牌 + 外观相似度高 + 商家多次被下架 | 外观相似 + 商家历史 + 案例先例 |
| 字段冲突 | 标题写"真丝"，OCR 读到 "Polyester" | OCR 与商品字段交叉验证 |
| 无依据宣传 | "7 天瘦身""医学专家推荐" | 提取宣称 + 查政策 + 查先例 |
| 弱信号叠加 | 多个弱信号单独看都能放行，合起来高风险 | 多源综合 |

### 13.4 不做方案级与组件级消融

评测保持**三套方案直比**：Rule / 一次模型调用 / Agent 跑同一份数据，差异就是"允许用多少基础输入之外的
信息"的整体差异。不做"预塞政策与先例文本"这类方案级变体消融，也不做逐工具裁剪的组件级消融 ——
它们都只服务一次性的必要性论证，却要评测框架长期背着一套实验配置。

**口径边界**：Agent 相对一次模型调用的差异是"工具 + 多步"的**整体**差异，
不可分解归因于"主动调查"这一项。工具的必要性改用**证据覆盖**如实标注（哪些案子的期望工具里有它），
期望为空的工具不做"不必要"的判定。

## 14. 范围：做什么、不做什么

### 14.1 最小闭环必须有的

1. 一个核心场景：潜在 IP / 品牌模仿 / 规避审核。
2. 传统机审初筛（简版规则引擎，能跑出三分流）。
3. 六个工具：商品、图片分析、OCR、商家、案例检索、政策检索。
4. 状态图编排的调查循环：显式状态机 + 预算护栏 + 动态挑工具。
5. 两类知识库：政策库与案例库。
6. 三分类决策 + 证据链输出。
7. 评测集与三方案对比框架（先小集跑通，再扩到含难例的正式集）。
8. 全链路轨迹、指标与成本统计。

### 14.2 支撑场景（第二步再做）

虚假 / 无依据宣传（提取宣称 + 证据推理）、商品字段冲突（多源交叉验证）。

### 14.3 明确不做

| 不做 | 为什么 |
|---|---|
| Multi-Agent | 单个案件的调查是"单智能体多步推理"，一个循环就能解决；拆多 Agent 只增加协调成本与上下文割裂 |
| MCP | 六个工具都是内部服务，统一接口 + 注册表已经够；要接外部或第三方工具时才需要 |
| 微调 / 训练模型 | 判定靠证据和政策，不靠"背答案"；评测集还没稳定就微调属于过早优化 |
| 知识图谱 | 案例与政策用向量 + 关键词检索已经够，图谱的复杂度收益不成比例 |
| 重型向量库（ES / Milvus 一类） | 语料是小语料，不引重型组件 |
| Redis / 消息队列 | 核心闭环不依赖它们；可选项不能成为默认路径的前置条件 |
| 一次性实验设施：阈值扫描、方案级与组件级消融 | 只服务一次性论证，却让评测框架长期背着配置面 |
| 横向铺开多个审核场景 | 先把一个难例的闭环证明清楚，再谈扩展 |
| 全量 Agent 审核 | Agent 的定位是复杂节点；全量交给它既贵又慢，还引入不确定性 |

## 15. 代码怎么分层

分包的理由只有依赖方向，不镜像目录树：

- **domain 独立**：案件、证据这类核心契约放这里，被初筛、Agent、评测三处复用。
- **agent 与 tools / rag 分层**：状态图依赖的是工具**接口**，不是具体实现（依赖倒置），
  方便测试替换，也方便将来换实现。
- **evaluation 独立**：评测是独立关注点，不污染业务代码。
- **screening / api / infra / observability** 各管一段：初筛与分流、对外入口、落库与存储、观测。

不变量：**同一个语义若存在多处实现，必须逐条等价，并由测试锁死**；只改一处视为缺陷。
