# 商品内容治理 · 复杂风险调查 Agent —— 技术方案

> 本文只写**技术方案**：架构、调查流程、状态契约、工具、检索、决策机制、数据与观测。
> 需求（解决什么问题、服务谁、边界、范围、验收口径）以 [01-requirements](01-requirements.md) 为准；
> 正确性底线（判定三态、证据红线、禁止静默降级等）以仓库 AGENTS.md 为唯一事实源，本文不重复；
> 评测口径细节以 [02-evaluation](02-evaluation.md) 为准。
> 字段、配置值、目录结构等实现现状以代码与版本库为准，本文不镜像。

## 1. 系统在链路中的位置

系统是嵌入现有审核链路的**复杂案件处理节点**：机审（确定性规则与传统模型）全量初筛，
分流出的复杂案交给本系统异步调查，产出三分类裁决 + 证据链。边界与定位的完整论证见 01 §4。

```
商品上架 / 改标题 / 改属性
   ↓
规则 + 传统模型初筛（同步、快、便宜，全量过）
   ↓
三分流：明确正常 / 明确违规 / 复杂低置信
   ↓
复杂低置信 → 复杂风险调查 Agent（异步、预算受限）
   ↓
PASS / REJECT / HUMAN_REVIEW
```

仓库内置的 screening 规则引擎是**上游机审的替身**，供独立运行与评测使用；
生产集成时机审结果由调用方传入，本系统不建设上游机审能力。

## 2. 整体架构：同步初筛 + 异步调查

### 2.1 为什么分两段

- 规则和传统模型是**同步确定性**链路：毫秒到秒级、可并行、不烧 token。
- Agent 是**慢、贵、结果带不确定性**的链路，只处理分流出来的复杂案（设计假设：复杂案只占全量的一小部分），
  异步消费 + 预算限制 + 失败重试。

这样 Agent 的引入**不会拖慢全量审核吞吐**，只是给复杂案追加一个"调查节点"。

### 2.2 每一层干什么

| 层 | 职责 | 关键点 |
|---|---|---|
| 接入 | 接收商品上架 / 变更事件 | 现在是同步 HTTP 入口（demo 形态）；生产形态为异步消费，消息队列在并发需求真实出现时再引入 |
| 同步机审 | 跑规则与传统模型，产出信号、风险分 | 确定性、全量、低延迟；本仓库内仅为替身（见 §1） |
| 分流 | 把结果分三堆：明确正常 / 明确违规 / 复杂 | **确定性规则，不是模型**；硬规则高分直接拒、无信号低分直接放、中间带进复杂队列 |
| 复杂调查 | 对复杂案做多步取证 | 异步 worker，状态图编排，预算受限 |
| 决策 | 输出结论并落库 | 自动结论落库并通知商家；HUMAN_REVIEW 是终态输出，人工裁决与回流在边界外（01 §4.1） |

技术选型上只需要记住两条：**调查用状态图编排**（显式状态 + 条件边 + 检查点，正好是这个循环需要的骨架），
**检索用关键词 + 向量混合**。具体用了哪些库、哪个版本，以仓库配置为准，本文不镜像。

## 3. 案件模型：输入是事实，输出是裁决 + 证据链

一条案件就是一次审核的完整上下文。输入是**商品事实快照**：标题、描述、属性、类目、品牌、SKU
这类文本与在库事实，以及机审已经产出的结果 —— 机审的结论作为**起点信息**带进来，避免 Agent 重复劳动。

输出是**结构化裁决 + 证据链**：三分类结论、风险等级、风险类型、支撑结论的证据、
引用的政策条款，加上这次调查的过程轨迹。证据链是核心 —— 以后有人问"这个商品凭什么这么判"，
答案必须在证据和假设轨迹里找得到，不能只存在于模型的上下文里。

两条口径不变：

- 支撑判定的证据必须带**可追溯引用**（引用到具体政策条款或具体先例），不可引用的材料撑不起拒绝。
- 风险类型走**受控词表**（见 §8.3），评测标签、政策库元数据、决策输出三者共用同一套词表。

字段名、字段清单与序列化形态一律以代码为准，本文只写语义。

## 4. Agent 的状态：显式、可序列化、可恢复

Agent 的状态必须是显式的、能序列化的、能持久化并恢复的，而不是藏在模型的对话上下文里。
这是"工程化的 Agent"和"一个 prompt 循环"的分水岭。

### 4.1 设计要点

1. **假设是状态的核心**：Agent 不是分类器，是假设验证器。每条假设有自己的验证状态，调查过程可解释。
2. **状态显式化并由框架持有**：状态图的检查点持有每步状态快照，供流式执行后读取终态。
   检查点不承担业务持久化职责（业务真相显式落 MySQL），也不承担评测重放职责。
3. **预算是状态的硬字段**：进入节点之前先检查预算，超限直接路由到转人工止损。
4. **结论依据与过程审计分开**：证据是前者，工具调用历史是后者，两者都进轨迹。
5. **图的终态只有一个**：收敛即终态。`PASS / REJECT / HUMAN_REVIEW` 是最终裁决的取值，不是图的状态；
   预算耗尽、工具失败、降级这些都通过裁决上的改判记录留痕，不另开状态。

### 4.2 状态契约

- **只装调查记忆与图内控制通道**：商品事实、假设、证据、待查问题、工具调用历史、预算、决策。
  运行标识与运行状态不进状态（运行状态在库里）。
- **证据一旦收集不可篡改**：证据合并遇到重复按去重键丢弃新增，绝不覆盖；工具调用历史和失败记录只追加。
- **不累积对话历史**：每个模型节点都从状态重新组装 prompt，一次调用内部的对话只活在这次调用里 ——
  这样状态可序列化、token 可预算。
- **边界由入参结构约束**：假设条数、待查队列长度、单轮计划里的工具数都由 schema 限定。
- **判定要过可验证约束**：提案可以来自模型，但终裁必须经 Gate 用事实校验；假设状态与自报概率不作为判定依据（见 §8.2）。
- **模型步失败怎么降级**：结构化输出校验失败先自动重试一次；仍失败则该节点返回降级结果并打标记，
  之后不再调用模型，统一按"证据不足"路由到决策，由确定性收口产出 `HUMAN_REVIEW`（硬规则命中除外）。
- **假设的生命周期**：待验证 → 被支持 / 被否定 / 查过但未能证实也未能证伪。最后一种要和"还没查"分开 ——
  它只是说这条线索查完没结论。假设状态**只用来引导调查和留痕**，最终裁决由证据事实决定，不由假设状态推导。
  假设在入口生成一次，运行中新冒出来的由复核节点追加。

## 5. 调查循环与图的分工

### 5.1 循环本身（与框架无关）

```
观察（读商品事实 + 已有信号 + 已有证据）
   ↓
提假设（生成 / 更新风险假设）
   ↓
定计划（验证哪条假设？还缺什么证据？）
   ↓
行动（动态挑工具并调用）
   ↓
观察（读工具结果，合并进证据）
   ↓
复核（依据新证据更新假设状态）
   ↓
决策（证据够 → 出结论；不够 → 回到计划，或转人工）
```

### 5.2 谁做什么：这是本项目最重要的工程决策

| 步骤 | 谁来做 | 为什么 |
|---|---|---|
| 图编排、条件边路由、预算记账 | 状态图 + 确定性 Python 路由函数 | 可靠、可测、成本可控 |
| 工具执行、结果反序列化、证据去重合并 | 确定性代码 | 不浪费 token |
| 提假设、定计划、复核证据、给决策提案 | 模型节点（结构化 JSON + schema 校验） | 这些需要语义推理 |
| 硬规则兜底（黑名单必拒） | 决策前的确定性收口 | 安全红线 |
| 状态快照 | 状态图检查点 | 流式执行后读取终态 |

选现成的状态图框架（LangGraph）而不是自研循环，是因为它的核心模型 —— 显式状态 + 图 + 检查点 + 条件边 ——
正好就是这个循环需要的骨架，可以直接省掉自写状态机与持久化的重复劳动。但框架**只负责编排骨架**，
下面这些仍是自研：预算护栏、硬规则兜底、证据去重、工具参数 schema、决策收口、轨迹落库。

> 关键边界一句话：**让模型做语义推理（节点内部），让确定性代码做路由与安全（条件边 + 护栏）。**
> 如果整张图交给模型决定怎么走，就会同时得到成本失控、不可控、不可测三个问题。

### 5.3 为什么是动态挑工具，而不是固定流水线

固定 `A→B→C` 会对每个案子无差别地调所有工具，纯属浪费（文本没命中时没必要翻商家历史）。
动态挑工具的依据是：**当前最值得验证的假设，需要哪条证据？** 由计划节点决定、条件边路由过去。
比如在库属性写着 "100% Polyester" 而标题宣称"真丝"，那就该优先调商品工具做字段交叉，而不是再去翻案例库。

这是 Agent 相对"固定工作流"的核心增量，也是评测里工具选择指标的来源。

### 5.4 一次调查走查（常见硬案：复古运动鞋）

| 轮次 | 干什么 | 结果 |
|---|---|---|
| 0 | 读商品事实：全部放行、品牌为空、没有品牌词 | 立起初始假设 |
| 1 | 最该查的是：商品在库事实是否与声明一致 | 调商品工具 → 品牌为空、类目与描述对不上，成为证据 |
| 1 | 复核 | 相关假设被支持，另一条被削弱 |
| 2 | 要确认商家是否有系统性行为 | 调商家工具（23 次相似上架 / 5 次下架 / 3 次改标题重上） |
| 2 | 复核 | 规避行为这条假设被支持 |
| 3 | 需要先例与政策支撑 | 查案例库（有高度相似先例，历史结论是拒绝）+ 查政策库（支持高风险转人工） |
| 3 | 复核 | 证据链完整，收敛 |
| 4 | 决策 | 证据充分，但"仿冒"是主观判定 → 转人工（高风险） |

注意最后一步：Agent 的价值不只是"自动判掉"，更在于**知道什么时候证据够了、什么时候该人介入**。

### 5.5 各节点的契约要点

| 节点 | 要点 |
|---|---|
| 提假设 | 入口执行一次；读商品事实，产出初始假设与初始调查队列 |
| 定计划 | 每轮说清"下一步验证哪条假设、调哪个工具、为什么"；没有值得做的动作就直接转决策 |
| 工具 | 确定性执行：按工具名 + 参数分发，反序列化结果、去重合并证据；单批调用按上限截断 |
| 复核 | 依据新证据更新假设状态、必要时追加假设；证据不够且预算没超就回计划，否则转决策 |
| 决策 | 模型只给**提案**，随后由确定性收口按 §8.2 的顺序定稿，改判与原因记在裁决上 |

防重复动作：计划节点反复提议同一个调用时，第二次即清空计划并视同"可以收尾"，不存在空转烧预算的死循环。

## 6. 工具：四个，各自回答一个问题

每个工具都要能回答"审核员为什么需要这条信息"，不为数量堆工具。

| 工具 | 回答什么 |
|---|---|
| 商品工具 | 这个商品的在库事实是什么？尤其品牌字段是不是真的空 |
| 商家工具 | 这个商家是不是在系统性地做类似的事？ |
| 案例检索工具 | 有没有类似且已有人工裁决的先例？结论是什么？ |
| 政策检索工具 | 当前有效的政策对这类情况怎么说？ |

一句话记住各自的不可替代性：商品工具是**在库事实锚点**，商家工具给的是**行为模式**，
案例工具给**先例参照**，政策工具给**判定依据**。

生产与评测共用这四个工具；评测里只有 agent 臂使用工具，rule 与 single 臂不看工具材料 —— 评测口径见 02。

工具抽象上只有两条：计划节点只输出"调哪个工具、带什么参数"，由分发器按名字调度并对参数做强校验；
**不做 MCP** —— 四个工具都是内部服务，统一接口 + 按名调度就够了。等到要接外部、第三方或跨语言的工具时，
标准化的价值才显现，那时候再引入。

数据来源按环境分：测试世界（``tests/inmemory_world.py``）读**最小种子数据**（够跑测试与回归即可，CI 不连外部数据源）；
生产入口与评测读真库与真实检索。种子是最小实现，不要求与真实库逐项等价，只要求业务行为一致。
**真链路不可用时必须显式失败并记为失败，不静默回退成种子数据** —— 这是"禁止静默降级"底线的机制落点。

## 7. 两类知识库（RAG）

### 7.1 政策库与案例库，作用不同

| 知识库 | 装什么 | 在什么时候用 |
|---|---|---|
| 政策库 | 审核规则、平台政策、违规判定标准（带版本与生效日期） | 调查中给出"当前适用的政策依据" |
| 案例库 | 历史人工审核案例（商品、证据、最终裁决、依据政策） | 调查中给出"相似案件先例"作为参照 |

要澄清一点：**RAG 不是让模型背规则的**（那是规则引擎的活），而是在调查过程中把政策依据和先例依据
**作为证据注入**，让结论有据可依、可引用、可审计。

### 7.2 怎么检索

- **混合召回（生产唯一口径）**：关键词（BM25）加向量相似度，RRF 融合后取前 K 条。独立的单路模式不作为架构能力，只允许存在于调试 / demo 入口。
- **元数据过滤**：按类目、风险类型、政策是否在有效期内过滤，避免召回到过期政策或不相关类目的案例。
  混合检索两路实现的过滤**语义必须逐条等价** —— 向量路把过滤下推到库里，关键词路只能在 Python 候选集上过滤，
  改一侧必须同步另一侧，并由测试锁死，否则漏召回只在带过滤时才暴露。
- **融合与截断**：两路结果用 RRF 融合后截断，控制注入上下文的量；不做重排序。
- **引用格式**：政策的引用要带政策编号、版本、条款原文；案例的引用要带案例编号与结论。
  进了证据链就必须能追溯回原始条款或原始案例。

### 7.3 分数与模式的口径（几条容易搞错的红线）

- **检索分不是语义相似度**。它是后端定义的检索分：关键词路是无界的原始分，向量路是距离的单调函数，
  混合路是 RRF 分，三者**量纲互不可比**。任何场合都不得把它叫成"相似度"。
- **不换算量纲、不设取值域约束**：排名只依赖单调性，换算没有收益；这个分往下只用于渲染证据行和落库审计，
  **不参与任何 Gate 判定** —— Gate 对案例与政策证据只判"有没有可引用的依据"，不读分值。
  用 min-max 之类把分数拉平属于伪造，不做。
- **单路模式不是架构能力**：生产、评测、回归一律跑混合模式；单路模式只能作为独立调试 / demo 入口存在，
  不得进入"评测 → Agent → 工具 → 检索"链路，也不得为了它保留模式开关。
- **建库必须显式指定余弦度量**：用错度量会让"像不像"的整体间距语义偏移，而且**不报错**，只是排名和分数一起失真。
- **写入与元数据**：同一条记录不会被覆盖，写入要先删后加；元数据的形状变了必须换集合名，
  否则旧库被原样复用，新过滤条件会**静默零命中**。
- **取回多少就是多少**：前 K 条不保证真的返回 K 条；检索真失败（服务不可达、集合不存在、编码失败）
  直接上抛，不另补一套检索兜底。
- **分词与索引各自持有**：不替换第三方库的全局符号，各检索器实例互不共享状态，并发下互不干扰。
- **不为测试引入假编码器**：生产、测试、回归、评测用同一个真语义模型，避免"测试里像、线上不像"。
- **内存版向量库对 id、维度之类的约束比真服务端宽松**，缺陷可能在单测全绿的情况下潜伏，
  只在真服务端暴露 —— 真服务端的集成用例不能省；反过来说，不装检索依赖的环境里
  这些用例整体跳过，不能声称"CI 覆盖了向量库"。

### 7.4 向量库选型与内容维护

语料是小语料，用 ChromaDB 就够了，明确不上 Elasticsearch、Milvus、知识图谱这类重型方案，降低工程复杂度。

案例库与政策库的内容更新（人工裁决沉淀为新案例、政策版本化替换）由**下游系统**承担，在本系统边界外
（01 §4.1）；本节只约束检索侧：检索范围按政策有效期与版本过滤，内容来源不进入判定逻辑。

## 8. 三分类决策机制

### 8.1 判定只吃事实，展示量不参与

转人工（abstention）的本质**不是"置信度低于阈值就交人"，而是"证据是否足以支撑一次安全的自动决策"**。
判定只看事实通道（证据链 + 覆盖三态 + 规则命中 + 预算/降级），不维护任何"安全信心"分数，也**不采信模型自报的
置信度**：

| 概念 | 一句话定义 | 用途 |
|---|---|---|
| 风险等级与风险强度（`risk_level` 等） | 风险本身的高低与强度 | **只用于展示、人工队列排序、统计**；不参与路由，也不参与判定 |

三分类的语义：

| 决策 | 含义 | 触发条件概要（完整规则见 §8.2） |
|---|---|---|
| PASS | 放行 | 没有任何维度匹配的阳性证据；没有规则侧阳性；本案必需的测量维度全覆盖且都是阴性 |
| REJECT | 违规，拒绝上架 | 命中 R-302 规避词（文本自证）；有带引用的可引用依据 |
| HUMAN_REVIEW | 转人工 | 两道 Gate 都没过，或命中弃权清单 |

### 8.2 决策规则：模型只提案，确定性 Gate 收口

决策分两层：**模型给提案，确定性 Gate 做最终校验**。收口按下面的顺序执行，任何一步不满足就改写成
`HUMAN_REVIEW`，并把改判原因记在裁决上：

1. **硬规则优先，模型不可覆盖**：调查中命中黑名单品牌（R-101）这类硬规则或硬违规，强制 `REJECT`；
   哪怕模型说 PASS，也以命中为准 —— 这是防漏放。
2. **弃权清单**：下列任一成立就转人工（哪怕提案是 PASS 或 REJECT）：
   - 本案必需的维度**本环境可测却没测**（属于可补救的取证缺口，先回环补测）；
   - 必需维度**在本环境测不了**（重跑也没用，不回环）；
   - 阳性不足以自动拒绝（只有弱信号、只有商家画像、或者没有可引用依据）；
   - 预算耗尽 —— 带上已经查到的证据转人工；
   - 任何一步降级。
3. **提案过不了对应的 Gate**：PASS 提案过不了 PASS Gate，或 REJECT 提案过不了 REJECT Gate。

**REJECT Gate** —— 可以自动拒绝，当且仅当下面全部满足：

- 命中平台规则里的**规避词（R-302，文本自证）**；
- 有**可引用依据**：至少一条带引用的政策条款或高度相似的先例证据 —— 这是防误伤，拒审同样是资损和商誉损失。

三条容易被放宽的红线，必须写清楚：

- **R-302 是本列表文本自证**，只有它授权自动拒绝；其余阳性（含商家行为画像）都不单独授权。
- **只有商家历史脏，不授权自动拒绝**。商家画像是针对该商家的统计，不能当成这一个商品违规的确证；
  它只能阻塞放行，把案子推向人工。
- **品牌词命中（R-102）同理：它只阻塞放行，不授权拒绝**。

**PASS Gate** —— 可以自动放行，当且仅当下面全部满足：

- 没有任何维度匹配的**阳性证据**（含仅商家画像这种）；
- 没有**规则侧阳性**（品牌词、规避词命中一律阻塞放行）；
- 本案必需的测量维度**全部覆盖，且结论是阴性**。

这里的三态要分清：证据承载"测过（含**阴性**结论）"这一类；"没测"和"本环境测不了"**不是证据**，
由 Gate 用"必需维度 × 证据有没有 × 环境能不能测"推导出来。**绝不为"缺席"造证据** ——
这样才能把"证明没风险"（可以放行）和"没查到风险"（应当转人工）区分开。

两条结构性约定：**本案需要测哪些维度，由案件的客观事实决定**（商品在库事实、商家、文本恒必需），
**不由模型的计划或假设决定**，否则判定会随模型的计划波动；**Gate 不采信模型自报的量**
（假设状态、概率、自报置信度都不作为判定依据），提案只决定走哪道 Gate。

### 8.3 风险类型受控词表

```
POTENTIAL_IP_RISK     疑似 IP / 品牌模仿
EVASION_PATTERN       规避审核行为模式
```

词表的业务取舍（为什么只做这两类）见 01 §4.3。评测集的标签、政策库的元数据、决策输出三者共用这一套词表，
跨产物的统计才有可比口径（指标口径见 02）。

### 8.4 风险等级不参与判定

风险等级只用于展示、人工队列排序、审核优先级与统计，**不作路由输入，也不作改判输入**，避免把展示口径
变成判定逻辑。典型反例：**高风险 + 证据不足 → 转人工**，而不是高风险就直接拒绝。风险高不等于可以自动判。

## 9. 预算护栏、安全护栏与终止性

### 9.1 预算：是保护上界，不是目标

四组上限 —— 模型调用次数、工具调用次数、token、执行时间 —— 都是**保护性的上界**。
正常案件的实际用量应当**明显低于上限**，余量是留给结构化输出校验失败重试、工具失败恢复和防无限循环的。

| 超了哪个 | 怎么办 |
|---|---|
| 模型调用次数 / 工具调用次数 | 停止调查 → 带上已收集的部分证据转人工；工具节点同一批调用也按上限截断 |
| token | 压缩上下文，或停止 |
| 执行时间 | 超时 → 转人工 |

- 检查发生在**每次进入节点之前**（条件边里的确定性代码），不是"跑完才发现超了"。
- 上限可以在**生产装配层**配置。
- 超限的语义是：**调查成本已超出可接受范围，证据又不足以自动判，转人工最稳妥** —— 这是正确的业务行为，
  不是失败。
- **评测不为跑分放宽档位**：正式评测的真实模型臂跑的就是生产预算上限。预算够不够用本身就是被测行为。
- 预算与阈值常量的拟合红线见 AGENTS.md；具体取值以代码为准。

### 9.2 安全护栏的机制落点

护栏的底线条款（硬规则不可被模型覆盖、自动拒绝必须有可引用依据、商家历史画像不单独授权拒绝、
禁止静默降级与静默失配等）以 AGENTS.md 为唯一事实源；本节只写它们在系统里的**机制落点**：

1. **硬规则兜底**在决策收口之前强制执行：命中黑名单、硬违禁即改判 REJECT，不经过模型。
2. **可引用依据校验**在 REJECT Gate 内做确定性检查：引用串必须能解析回真实政策条款或先例（见 §8.2）。
3. **个人信息**：工具返回给模型之前先脱敏（商家联系方式之类），模型输出不落地敏感字段。
4. **决策可审计**：每个决策都带支撑它的关键证据与必要轨迹，能回溯到"哪个工具给的哪条证据
   导致了这条结论"。不为"将来可能查"而保存全部中间状态。
5. **幂等**（同一商品同一版本只审一次，需求见 01 §3）由落库层去重实现，防止重复消费导致重复计费。

### 9.3 一定停得下来

- 图里**唯一的回环**是「计划 → 工具 → 复核 → 计划」；决策节点没有出边。离开回环只有三个出口：
  收敛、计划侧主动收尾、预算超限。
- 每一轮至少消耗 1 次计划的模型调用 + 1 次复核的模型调用，所以**由模型调用上限可以直接推出回环轮数的上界**
  （实际因为早停更少）。
- 空转也被堵死：计划反复提同一个动作，第二次就清空并视同收尾；工具只有四个，加上调用上限兜底；
  任何节点一步降级就短路进决策。
- 路由、预算、收敛、Gate **全是纯函数**（无随机、无模型）—— 同一个状态必定走向同一个后继，
  不存在"同状态走不同分支"的非确定性死循环。

## 10. 数据怎么落（不镜像表结构）

表的划分口径是三类：**商品事实**（商品）、**商家画像**、
**案件与运行轨迹**（案件、运行、轨迹、证据、结果）。有一条去重原则：同一个事实不在两处存
—— 检索用的向量归向量库，不进业务表。

落库约定：主键统一用雪花号，版本字段做乐观锁，状态字段加索引，半结构化数据用 JSON 列；
迁移是手写的 SQL，模型校验与序列化交给 Pydantic。字段与建表语句以迁移文件和 ORM 映射为准。

**单一事实来源优先**：同一事实只保留一处权威表示；确有第二处时必须有明确业务价值，
且不得成为可独立漂移的第二真相。不为未来可能的审计需求提前落字段。

**Redis 与消息队列现在不引入**：核心闭环不依赖它们（可选项不能成为默认路径的前置条件）。
真出现并发与异步需求时，它们的落点是幂等去重、限流、worker 抢占案件的分布式锁、热点缓存，
以及请求投递、复杂案投递、人工裁决回流这三个主题加重试与死信。

## 11. 观测与记账

观测分四层，各管一段，互不替代：

| 层 | 记什么 | 落在哪 |
|---|---|---|
| Agent 内部轨迹 | 每一步的工具名、参数、结果、token、耗时 | 落库，这是业务审计的真相所在 |
| 模型调用级 | 每次调用的 prompt、输出、token、成本 | Langfuse |
| 链路级 | 一个请求从接入到决策的全链路 | 链路追踪（OpenTelemetry 一类） |
| 业务指标 | 决策分布、转人工率、自动化率、各风险类型占比 | 指标表 / Prometheus |

**为什么要落库**：申诉调查与结果溯源（"这个商品为什么被拒"）要靠它，成本能算到关键步骤。
这是工程化 Agent 和调 API 的 Demo 的本质区别。

记账口径有一条不能破：**桩路径下 token 为 0、没有费用、耗时约等于 0 是真实情况**（没有真实模型调用），
**绝不填估算值上去**；真实 token 与耗时只出现在走真实模型的路径。两个世界的数字不得混算，也不得互相暗示。

观测组件缺凭据时降级为全空操作，不联网、不阻塞主流程 —— 这条只约束观测，它不影响主链路的真实性声明。

## 12. 技术取舍：明确不做

| 不做 | 为什么 |
|---|---|
| Multi-Agent | 单个案件的调查是"单智能体多步推理"，一个循环就能解决；拆多 Agent 只增加协调成本与上下文割裂 |
| MCP | 四个工具都是内部服务，统一接口 + 注册表已经够；要接外部或第三方工具时才需要 |
| 微调 / 训练模型 | 判定靠证据和政策，不靠"背答案"；评测集还没稳定就微调属于过早优化 |
| 知识图谱 | 案例与政策用向量 + 关键词检索已经够，图谱的复杂度收益不成比例 |
| 重型向量库（ES / Milvus 一类） | 语料是小语料，不引重型组件 |
| Redis / 消息队列 | 核心闭环不依赖它们；可选项不能成为默认路径的前置条件 |
| 一次性实验设施：阈值扫描、方案级与组件级消融 | 只服务一次性论证，却让评测框架长期背着配置面；工具必要性用期望工具覆盖如实标注（见 02） |

业务范围层面的不做什么（虚假宣传、字段冲突、人工工作台、全量审核等）见 01 §7，本文不重复。

## 13. 代码怎么分层

分包的理由只有依赖方向，不镜像目录树：

- **domain 独立**：案件、证据这类核心契约放这里，被初筛、Agent、评测三处复用。
- **agent 与 tools / rag 分层**：状态图依赖的是工具**接口**，不是具体实现，便于在真正需要时替换依赖
  （真实库 / 真实检索 / 测试替身）。不为"将来可能换实现"增加额外抽象层。
- **evaluation 独立**：评测是独立关注点，不污染业务代码；但它**共享生产核心逻辑**，不复制第二套业务实现或数据世界。
- **screening / api / infra / observability** 各管一段：初筛与分流、对外入口、落库与存储、观测。

不变量：**同一业务语义只保留一处实现**。确因依赖隔离必须有两份时，只对会造成静默错误的部分加等价守护 —— 不追求两套世界逐项等价。
